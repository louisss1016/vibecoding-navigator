# Agent 架构技术规范（三板斧融合）

这个专家回答：**做一个 Agent 项目，材料怎么进、能力怎么接、编排怎么组织、凭什么可信、成本怎么守。** 按三板斧组织：第一板斧（材料与能力入口）→ 第二板斧（编排）→ 第三板斧（评测与成本）。普通 Web/后端项目不用这个专家。

> 核心信念：**模型不是安全边界**。模型生成调用意图，授权、拦截、审计、确认必须在模型外部完成。Agent 能力越强，错误动作的破坏半径越大。

## 30 秒定位：我该看哪节

全文按三板斧组织，但**不用顺序读**。先建主链路骨架，再按问题跳读：

```text
材料五类型 → 能力入口 → Agent Loop → 评测 → Token 治理
(要什么)    (怎么接)    (怎么推进)   (凭什么可信) (怎么守预算)
```

| 你的问题 | 看哪节 |
|---|---|
| Agent 该看什么材料、材料从哪来、缺材料怎么办 | 第一板斧 · 材料五类型 + 失败语义 |
| 能力怎么接：函数 / MCP / CLI，选哪个 | 第一板斧 · 三个能力入口的分工 |
| RAG 还是知识库 | 第一板斧 · RAG vs 知识地图 |
| 模型会编造 / 结论不可信 | 第一板斧 · 失败语义 + 第三板斧 · 评测对象 |
| Loop 停不下来 / 跑着跑着忘了目标 | 第二板斧 · Agent Loop（停止条件三件套） |
| Prompt 怎么写 | 第二板斧 · Prompt 六职责 |
| Memory / Skill / Tool 怎么分工 | 第二板斧 · 三者对比表 |
| 单 Agent 不够了？要不要上多 Agent | 第二板斧 · 升级判据（先对失效信号表，不许跳级） |
| 多 Agent 怎么分工、怎么通信 | 第二板斧 · 角色分工表 + 四问 |
| 上下文爆了 / Token 烧钱 | 第三板斧 · Token 治理 + 工程模式 · 缓存三层 |
| 工具调用危险 / 怕 prompt injection | 第一板斧 · 能力边界七条 + 工程模式 · 两步授权 |
| 怎么证明 Agent 做对了 | 第三板斧 · 评测对象 + 六环节 + 五层测试面 |
| 评测挂了，该改哪里 | 第三板斧 · 审计回流表 |
| Agent 上线后看什么指标（不能只有 CPU） | 第三板斧 · AI 线上监控四层指标 |
| AI 项目有哪些典型死法 | 第三板斧 · 四个坑 |
| 要的工程模式（熔断/退避/降级/日志/Trace） | 第三板斧 · 工程模式速查 |

**什么时候不用这个专家**：见文末——纯静态页、常规 CRUD、单轮问答别过度设计。

## 第一板斧：场景材料与外部能力

### 材料五类型：先判断"需要什么"，再谈"怎么接"

| 材料类型 | 典型来源 | 对 Agent 的意义 | 常见风险 |
|---|---|---|---|
| 本地材料 | 文件、代码、日志、上传文档 | 任务的直接上下文 | 太长、噪声多、版本不一致 |
| 外部知识 | 文档库、历史案例、SOP、网页 | 领域知识和背景依据 | 召回错、过期、来源不明 |
| 结构化系统 | API、数据库、工单、指标平台 | 实时状态和业务事实 | 权限、行级数据、写操作风险 |
| 工具结果 | CLI、Tool Calling、MCP Tool | 可执行动作后的反馈 | 参数错、结果过大、危险命令 |
| 知识地图 | LLM Wiki / CodeWiki 类结构 | 可索引、可追溯的知识结构 | 索引过粗、正文缺证据 |

原则：材料设计不是"越多越好"，而是区分**必要证据**和**噪声**。缺材料时暴露"缺什么"，不是让模型猜。

### 三个能力入口的分工（不是替代关系）

| 能力 | 回答的问题 | 适合场景 |
|---|---|---|
| Tool Calling | 模型如何表达"我要调用工具" | 函数、API、查询、计算 |
| MCP | 外部能力如何被标准化接入和治理 | 企业系统、远程服务、跨客户端复用 |
| CLI | 本地工具链如何被高效执行 | 搜索（rg）、Git、测试、构建、批处理 |

选型口诀：**本地成熟工具链走 CLI；跨系统要治理的走 MCP；一次性的函数/查询走 Tool Calling。**

### RAG vs 知识库/知识地图

| 对比项 | RAG | LLM Wiki 类知识组织 |
|---|---|---|
| 核心问题 | 从资料中取哪些片段 | 资料本身如何组织 |
| 强项 | 动态召回相关内容 | 提供结构和导航 |
| 风险 | 召回错、片段缺上下文 | 索引漂亮但证据不足 |

RAG 关心分块/embedding/top-k/混合检索/召回失败与生成失败的区分；Wiki 关心分层/索引与正文的边界/从概念跳到依据。**信息已在上下文或需实时精确查询时，用 Tool/API，不用 RAG。**

### Provider / Capability / Tool 三层不能互相替代

```text
Strategy / Skill（流程）
    ↓
Capability（产品能力：quote / financials / portfolio-risk）
    ↓
Tool（执行原子：get_quote / get_kline）
    ↓
Provider Adapter（外部系统：哪家数据源/哪个服务）
```

Capability 说"产品要完成什么"，Tool 说"执行一个什么动作"，Provider 说"由哪个外部系统完成"。业务层只依赖 Capability，换 Provider 不动业务代码。

### 能力边界七条（接任何外部能力都要标）

1. 只读 / 写 / 外部副作用分级（ActionRisk: read / write / external_side_effect）
2. 高风险动作必须人工确认（HITL）
3. 路径、网络、数据库权限限制
4. 命令白名单 + 危险命令拦截
5. 工具输入输出日志（审计）
6. 结果截断、摘要、外置化——**工具输出过大时保留结构化摘要和外置引用，不把原始结果无限塞进上下文**
7. Prompt injection 防护：特权数据与工具不与用户原文同一上下文；模型生成的工具调用必须经 Schema 校验 + 权限检查 + 速率限制后才执行

### 失败语义（结果信封）

```ts
interface ProviderResult<T> {
  data?: T;
  provenance: { providerId, fetchedAt, marketTime?, delayed?, stale? };  // 溯源
  quality: 'complete' | 'partial' | 'stale' | 'unavailable';
  missingFields?: string[];   // partial 时标明缺什么
  fallbackUsed?: boolean;
  error?: { code, message, action? };  // action = Recovery Action
}
```

- Provider 不可用 → `unavailable` + Recovery Action，不是崩掉
- 字段缺失 → `partial` + `missingFields`，**不能用模型猜补**
- 数据过期 → `stale`，保留结果但降低结论强度
- 开发纪律：**先用固定 Mock 跑通链路，再替换真实 Provider，失败可回 Mock**

### 第一板斧验收

- 同一能力可由不同 Provider 返回，业务层无感
- 缺失字段不会变成 `undefined` / `NaN` / 假数据
- 每个关键结果能回答"来自哪里、什么时候获取、是否延迟"
- 高风险 Tool 没有绕过权限直接执行
- 能写出"输入 → 材料/能力 → 结构化结果"最小链路，并说清成功 / 缺材料 / 越权三种走向

## 第二板斧：能力编排与推理融合

### Agent Loop 是执行骨架

```text
理解任务 → 选择动作 → 调用工具/读材料 → 接收观察 → 更新判断 → 继续或停止
```

ReAct / Plan-and-Execute / Reflexion / LangGraph 都在回答同一个问题：模型如何在状态、工具和反馈中推进任务。**没有 Loop，Agent 退化成聊天；没有停止条件和错误恢复，Loop 变成失控循环。** 每个 Loop 必须显式定义：停止条件、最大步数、失败恢复路径。

### Prompt 是推理控制面（六职责）

| 职责 | 说明 |
|---|---|
| 任务边界 | 当前做什么、不做什么 |
| 角色约束 | 用什么身份和判断标准 |
| 输出格式 | 结果必须如何结构化 |
| 工具原则 | 什么时候该调、什么时候不该调 |
| 失败处理 | 信息不足/工具失败/低置信度时怎么做 |
| 证据约束 | 结论是否必须带来源、风险和不确定性 |

**Prompt 只控制当前任务行为。** 稳定流程沉淀为 Skill，长期信息进 Memory 或知识系统——不要把全部背景塞进 System Prompt。

### Memory vs Skill vs Tool

| 概念 | 解决什么 | 典型内容 | 常见误区 |
|---|---|---|---|
| Memory | Agent 知道了什么 | 任务状态、用户偏好、历史事实、已验证结论 | 当聊天记录全量塞 |
| Skill | Agent 应该怎么做 | 步骤、检查清单、模板、输出边界 | 当长 Prompt 或单个 Tool |
| Tool | 执行原子动作 | 读文件、搜索、调 API、跑命令 | 承载完整业务流程 |

### 什么时候单 Agent 不够（多 Agent 升级判据）

**默认顺序，不许跳级**：单 Agent + Tool → 单 Agent + Skill → 单 Agent + Workflow → Router + Worker → Synthesizer + Critic。

| 失效信号 | 根因 | 该不该升级 |
|---|---|---|
| 上下文越来越长，模型遗忘前文 | 窗口与注意力稀释 | 先压缩/外置（见 Token 治理），不行再拆 |
| 一个角色既要生成又要挑错，自审流于形式 | 生成者天然偏袒自己输出 | **该上 Generator + Critic** |
| 任务有天然可并行的独立子任务 | 串行浪费且互相干扰 | **该上 Router + Worker** |
| 不同子任务需要不同工具权限/系统访问 | 权限混用放大风险 | **该按角色隔离权限** |
| 任务需要不同专长（检索+推理+校对） | 单 Prompt 难表达多种判断标准 | **该按专长分工** |
| 简单工具调用、单轮问答 | 本就不复杂 | **不该上** |
| 只是为了显得架构复杂 | —— | **不该上** |

多 Agent 的价值不是"多个模型一起想"，而是**角色、上下文、工具权限和责任边界的拆分**。拆完没有清晰边界和交付契约，只是把混乱复制 N 份。

### 角色分工表

| 角色 | 职责 | 不负责 |
|---|---|---|
| Router | 拆分任务、选择 Worker | 不直接生成最终结论 |
| Worker | 处理一个证据域/子任务 | 不修改全局状态 |
| Synthesizer | 聚合证据生成报告 | 不绕过证据约束 |
| Critic / Auditor | 检查事实、证据、逻辑、风险 | **不直接执行原任务** |

进入多 Agent 必须回答四问：**分工**（按角色/阶段/数据源）、**通信**（消息总线/共享状态/黑板）、**冲突**（投票/仲裁/升级人工）、**状态**（谁记录、谁恢复）。角色之间**只传结构化中间结果，不传无边界的完整聊天记录**。

### 持久化与恢复语义（多步任务的最低要求）

- Session 隔离：两个会话同时跑，上下文不串
- 重启后恢复 Session 和最近 Run
- 事件按 sequence 排序，重复事件不重复应用
- 崩溃后 Run 进入 `failed`，不是永久 `running`
- Stop/Cancel 后不继续写入伪造的完成事件

## 第三板斧：评测、审计回流与 Token 治理

### 评测对象不是最后一段文字

Agent 评测必须看 Trace：质量不只在最后一句话，也在它做了什么、怎么做、有没有绕过边界。五维：Outcome / Trajectory / Evidence / Safety / Cost。

### AI 应用五层测试面（每层各测什么）

不要只测"最后答案对不对"。按层建立测试对象，golden cases 的 `category: agent` 用例按层归属：

| 层 | 测什么 |
|---|---|
| Model 层 | 准确性、稳定性（同问多次结果一致）、格式遵循、幻觉、安全拒答 |
| RAG 层 | Recall、Precision、Context Relevance、引用正确性（citation 对得上原文）、知识新鲜度、权限隔离（没权限的文档检索不到） |
| Tool/MCP 层 | 工具选择对不对、参数正确性、权限、失败处理、重试、幂等（重复执行不产生二次副作用） |
| Agent 层 | 任务完成率、步骤正确率、工具调用正确率、错误恢复、循环控制（不绕圈不失控）、成本、延迟 |
| Product 层 | 用户是否真的完成业务目标、是否节省时间、是否降低人工成本、是否降低错误率——**模型答得好 ≠ 用户解决了问题** |

企业知识库 / RAG 上线前过一遍治理八问：谁可以看（权限隔离）？数据来自哪里（来源可信）？多久更新（新鲜度）？谁维护？删除后多久生效（失效传播）？版本如何管理？权限如何继承？如何审计？

### 评测工程化六环节

| 环节 | 回答的问题 |
|---|---|
| Golden Cases 用例集 | 哪些真实任务必须永远通过？失败样例怎么沉淀成回归用例？ |
| 三类评分器 | 哪些用确定性检查？哪些 LLM-as-a-judge？哪些必须人工？ |
| 基线管理 | 这次改动变好还是变坏？和哪个版本比？ |
| 稳定性 pass^k | 同一用例跑 k 次都过，还是碰运气？ |
| Trace 工程化 | 过程证据能否复现、能否还原 Agent 做过什么？ |
| CI 回归 | 评测能不能每次改动后自动跑？ |

### 审计回流表（评测不通过时改哪里）

| 审计问题 | 回流方向 | 修正动作 |
|---|---|---|
| 缺材料 | 第一板斧·材料与能力 | 补充读取、检索、工具调用 |
| 数据过期/来源不明 | 第一板斧 | 降级结论、补 provenance 或重取 |
| 推理不闭合 | 第二板斧·编排 | 重组推理链、调 Prompt、调 Skill |
| 证据不足 | 第一 + 第二板斧 | 追溯来源、补证据、降低断言强度 |
| 权限/隐私风险 | 安全门禁 | 阻断、降级、请求人工确认 |
| 格式不达标 | 输出契约 | 重新组织报告/结论/风险点 |
| 超成本预算 | 第二/第三板斧 | 压缩、减少重复调用、降级或终止 |

修正之后**必须用同一失败用例重跑**，验证问题真的解决——不是"再生成一次碰运气"。

### Token 治理：省是技术，预算是治理

| 视角 | 归属 | 回答的问题 |
|---|---|---|
| 压缩/裁剪/缓存/子 Agent 隔离 | 第二板斧 | 怎么省 |
| 预算设定/成本可观测/成本审计/成本回归 | 第三板斧 | 该不该花、花得对不对、有没有漂移 |

成本与质量的张力（审计要盯的三条）：过度压缩 → 证据丢失 → 事实可靠性下降；过度裁剪工具结果 → 观察不充分 → 推理跳步；过早终止 Loop → 任务未完成。核心判断是"在证据完整性和预算之间找平衡"，不是越省越好。tiktoken 本地计数只是估算，以服务商 usage 返回对账校准。

### AI 线上监控不能只有 CPU

Agent 项目上线后按四层观察（五层测试面的线上化，落地细节配合 deploy-ops 的监控三件套）：

| 层 | 指标 |
|---|---|
| 技术指标 | Latency、Error Rate、Token Usage、Cost、Throughput |
| 模型指标 | Eval Score、Hallucination Rate、Refusal Rate、Output Quality |
| Agent 指标 | Task Success、Tool Call Success、Retry Count、Loop Count、Human Intervention |
| 业务指标 | 完成率、转化率、节省时间、用户满意度 |

判断标准：**真正有价值的监控不是"CPU 50%"，而是"用户完成核心业务的成功率下降"**。可观测性 + 评测是 Agent 上线后的持续质量基础，不是附加功能。

### 工程模式速查（实现时直接用）

- **三态熔断器**：Closed 正常转发统计失败 → Open 快速失败进冷却 → Half-Open 放少量探测，成功回 Closed 失败回 Open。熔断打开时不再重试下游，走降级。
- **指数退避**：`wait = min(cap, base * 2^attempt + jitter)`，jitter 防惊群。可重试：超时/连接错误/429/部分 5xx；不可重试：401/403/400/内容政策拒绝。
- **降级三形式**：模型降级（强→弱）、功能降级（多步 Agent→单轮问答）、输出降级（长文→要点）。降级必须可观测（日志标 `degraded=true`）。
- **缓存三层**：精确缓存（请求哈希，实现简单命中率低）/ 语义缓存（embedding 相似度，防"相似但意图不同"，敏感场景提高阈值或禁用）/ 结果分层（热问题走缓存，需 TTL 与失效）。缓存键必须含租户、模型版本、Prompt 版本、工具集版本，防串味。
- **结构化日志**：JSON 一行一条，必备字段 `timestamp/level/trace_id/span_id/step/model/latency_ms/token_usage/error_code`。切忌只打一大段自然语言。
- **Trace/Span**：Trace = 一次用户请求全程；Span = 一次 LLM 调用/工具执行/检索；`span_id/parent_span_id` 构成树，还原动态多步路径。每步记录 `step_index、thought 摘要、tool_name、tool_args（脱敏）、observation 摘要、耗时、重试次数、是否降级`。生产日志脱敏 + 采样。
- **工具参数校验**：JSON Schema（`additionalProperties: false`）+ 范围检查 + SQL 参数化；模型提议 → 策略引擎批准 → 执行（两步授权），不信任模型输出的任何工具调用。
- **小模型做分类/路由/摘要，大模型做最终生成**；非实时场景用 Batch API 或合并请求。

### AI 项目特别容易踩的四个坑

1. **模型强 ≠ 业务价值高**：模型回答得很好 ≠ 用户解决了问题。评测必须问到 Product 层（见五层测试面最后一行）。
2. **Demo 成功 ≠ 生产成功**：Demo → 真实数据 → 真实权限 → 真实并发 → 真实异常 → 真实成本 → 真实用户，每一关都是过滤网。开发期用 Mock 跑通链路，上线前必须用真实 Provider 重跑主链路（第一板斧失败语义的纪律）。
3. **没有 Eval 就无法稳定迭代**：Prompt 改了，A case 升、B case 降、C case 未知——没有回归基线，你甚至不知道自己变好了还是变坏了。这就是评测工程化六环节存在的原因。
4. **Tool/MCP 接通 ≠ Agent 可用**：接通只是起点。必须验证：选没选对工具、参数对不对、权限对不对、失败怎么办、超时怎么办、重复执行怎么办（幂等）。

## 什么时候不用这个专家

- 纯静态页面、常规 CRUD、不接 LLM 的项目（去对应栈专家）
- 单轮问答、无工具无多步的简单应用（还不到 Agent 的复杂度，别过度设计）
