# 存量项目改造（Brownfield）：已有代码库怎么下手

绿地项目（从零开始）走 `questioning-rules.md` 六问。但真实场景里一半以上的项目是**接盘一个已经存在的代码库**——这时候直接套绿地模板会翻车。这个文件是存量项目的 preflight 补充。

## 什么时候用这个文件

- 项目目录里已经有能跑的代码，不是空目录
- 用户说"帮我改一下这个项目 / 加点功能 / 修个 bug"
- 接盘别人的仓库、或者自己几个月前的项目

## 第一步：侦察（先于一切提问）

在问任何需求之前，先让 AI（子 agent）做只读侦察。开口 prompt：

```
请只读检查当前项目，不要修改任何代码。
我要知道【用户任务】现在是怎么完成的。最后只告诉我：
1. 技术栈和启动方式（怎么装、怎么跑、怎么测）
2. 现在的流程是怎样的（从入口到结果）
3. 哪一步最不顺
4. 你建议的最小下一步是什么
不要改代码，不要提大重构。
```

侦察输出固化为项目根目录的 `RECON.md`（模板见下）。

## 第二步：危险信号排查（比需求更优先）

侦察时发现以下任何一条，**先修它再谈新功能**——它们是上线事故的高发源头：

| 危险信号 | 为什么要先修 |
|---|---|
| 没有 lockfile（package-lock.json / requirements 固定版本） | 依赖漂移，换台机器就装出不同的环境 |
| 密钥硬编码在代码里 | 已经泄露（只要 push 过就算），先轮换 |
| 没有测试、没有 golden cases | 改任何东西都没有安全网，先建主链路的回归用例 |
| 数据没有备份 | 改 schema 改崩了无法恢复 |
| 构建/启动命令不明（README 过时或缺失） | 先把"怎么跑"搞清楚，否则一切验证都无从谈起 |
| 主分支有大量未提交/半成品代码 | 先 git 纪律整理（见 git-discipline.md），再动手 |

## 第三步：带着侦察结果走 preflight

侦察完再走标准六问（谁用/现在怎么解决/第一版做哪条链路/怎么算完成/不做什么/硬约束），但有两处不同：

1. **MVP 定义要考虑存量兼容**：新功能不能破坏现有用户的数据和习惯。PROJECT.md 的"验收标准"里必须有一条"老用户升级后原有数据/功能不受影响"。
2. **技术债显式入账**：侦察发现的债务（结构乱、无测试、过期依赖）列进 PROJECT.md 的"约束"或专门的"技术债"section，决定哪些本轮还、哪些挂着但记录在案。**不要在功能切片里顺手重构**——重构是独立切片（ownership-matrix 场景 3）。

## RECON.md 模板

```markdown
# RECON — 存量项目侦察记录（<日期>）

## 现状流程
【用户任务现在怎么完成的，从入口到结果，标出最不顺的步骤】

## 技术栈
- 语言/框架/数据库/部署：【】
- 启动：【命令】
- 测试：【命令 / 无】
- lockfile：有 / 无

## 危险信号
- [ ] 无 lockfile
- [ ] 密钥硬编码（位置：）
- [ ] 无测试
- [ ] 无备份
- [ ] 构建命令不明
- [ ] 其他：【】

## 技术债清单
| 债务 | 影响 | 处置（本轮还 / 挂账） |
|---|---|---|

## 建议的最小下一步
【一个切片定义：用户做什么 → 系统应该返回什么】

## 兼容性约束
【新功能不能破坏的现有行为/数据】
```

## 常见错误

- **跳过侦察直接问需求**：不知道现在怎么跑的，问出的需求全是空中楼阁。
- **接盘就大重构**："这代码太乱了，我重写一遍"——重写是最大的切片，没有回归网的重写等于赌博。先建 golden cases，再谈重构。
- **把危险信号当普通功能排期**："密钥硬编码下周修"——它比任何新功能都紧急，push 过的仓库密钥即泄露。
- **侦察让 AI 改代码**：侦察必须只读。让 AI 边看边改，你既得不到真实的现状报告，也不知道它改了什么。
