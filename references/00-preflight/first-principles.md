# 第一性原理拆需求

用户描述需求时，说的通常是"我以为的方案"，不是"真正的问题"。这一步要把方案拆回本质。

## 四象限拆解

把用户说的每一句话归到下面四类：

### 1. 绕不开的硬事实

不管怎么做都成立的东西。比如：
- "用户的数据必须存本地，因为他不想注册账号"
- "这个 app 必须离线能用"
- "响应时间不能超过 1 秒，否则用户会关"

**处理方式**：这些是架构约束，不能妥协，写进 `PROJECT.md` 的"已锁定决策"。

### 2. 习惯性接受但没验证的假设

用户觉得"应该这样"，但其实没证据。比如：
- "用户一定想要深色模式"
- "这个功能必须有图表"
- "大家都用 React，那我们也用 React"

**处理方式**：标记成"待验证假设"，写进 `PROJECT.md`。这些假设在 MVP 阶段不实现，等真实用户反馈再说。

### 3. 真正想实现的目标

用户嘴上说的方案背后，真正想达成的结果。比如：
- 他说"我要做个待办 app"，真正目标可能是"我自己每天三件事，写完就划掉，不要复杂"
- 他说"我要做个聊天工具"，真正目标可能是"我和朋友之间传文件比微信方便"

**处理方式**：这是项目的北极星，写进 `PROJECT.md` 的"一句话目标"。所有功能都要服务这个目标。

### 4. 现实资源与约束

- 我一个人做，两周内出第一版
- 我不会 DevOps，部署要简单
- 预算就够一个免费数据库

**处理方式**：写进 `PROJECT.md` 的"约束"，技术选型和架构设计都要受它约束。

## 怎么拆

对用户说的每一句关键描述，问自己三个问题：

1. **这是事实还是假设？** 有证据吗？还是他觉得应该这样？
2. **这是手段还是目的？** 他要的是这个东西本身，还是这个东西能帮他完成的事？
3. **去掉这个会怎样？** 不做这个功能，用户还能不能完成他要做的事？

如果去掉某个功能用户还能完成核心目标，那它就不是 MVP 必须的。

## 输出

拆完之后，你应该能写：

```
一句话目标：用户在 [场景] 下，通过 [动作]，就能 [完成的事]。
硬约束：[3 条以内]
待验证假设：[3 条以内，MVP 阶段不实现]
约束：[时间/技术/预算]
```

把这个填进 `templates/PROJECT.md.tmpl`。

## 常见错误

- **把用户的方案当需求**：用户说"做个微信小程序"，你就做小程序。但他真正要的可能是"手机上能快速记笔记"——一个 PWA 或原生 app 可能更合适。
- **把假设当事实**：用户说"用户需要多端同步"，你就上云数据库。但可能他的目标用户根本不需要。
- **忽略约束**：用户说"两周内出第一版"，你设计了个微服务架构。约束要反过来限制架构，不是被架构无视。
