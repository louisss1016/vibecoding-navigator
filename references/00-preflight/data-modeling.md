# 库表设计基线：先想清楚数据，再碰数据库

> 本文件管两件事：**数据库别选错**（真实项目一把梭 SQLite 是常见事故）+ **表要设计过再建**（不是代码写着写着随手加字段）。派工单涉及数据存储时，先过本文件。

## 第一件事：数据库选型，看项目性质不看省事程度

| 项目性质 | 选什么 | 理由 |
|---|---|---|
| 演示/教程/一次性验证 | SQLite | 零部署，用完即弃，不需要迁移 |
| 本地单机工具（单用户、数据跟本机文件走） | SQLite | 合理且常见，不是将就 |
| 桌面应用内嵌数据 | SQLite | 嵌入式场景的标准答案 |
| **真实项目**（多用户、要上线、数据要长存、要备份） | **PostgreSQL / MySQL** | 并发写入、权限体系、备份恢复、运维生态，SQLite 三项都弱 |
| 高并发写入、复杂分析查询 | PostgreSQL | JSONB、窗口函数、扩展生态 |

**红线**：以"MVP 先省事"为理由给真实项目选 SQLite，是把迁移成本留到最贵的时候。SQLite → PostgreSQL 的迁移不是改个连接串——并发模型、类型严格度（SQLite 的弱类型会让脏数据活到生产）、备份方式全不同。要么确定这是 demo/单机，要么直接上真数据库。

**触发迁移的信号**（出现任意一条，别犹豫）：第二个用户要同时写 / 要部署到服务器 / 要定时备份 / 数据量超百万行 / 需要复杂权限。

**选型结论必须写进 PROJECT.md 的技术栈表**，格式：`数据库：PostgreSQL（真实项目，多用户并发）` 或 `数据库：SQLite（本地单机工具，无需迁移）`——带上理由，不写裸名字。

## 第二件事：表结构设计，建表前过这五问

### 1. 实体从哪来：从用户故事倒推，不从代码结构正推

把核心用户故事念一遍（"商家发布一个商品""用户下单""仓库收货"），每个故事里的名词就是候选实体。**不要**按代码分层（controller/service/dao）想表——那是代码结构不是数据模型。

### 2. 关系先画再建

- 一对一 / 一对多 / 多对多，先分清。多对多必须建关联表（如 `order_item` 关联订单和商品），不要在一边存逗号分隔的 id 列表——那是查询灾难的开始。
- 外键加不加是权衡：小项目加了保数据干净，分库/高性能场景可能不加靠应用层保。**默认加**，明确不加要写理由。

### 3. 命名规范（全库统一，建第一张表前定死）

- 表名复数蛇形（`order_items`），列名蛇形（`created_at`）。
- 主键统一 `id`（bigint 自增或 uuid，全库一种，不混用）。
- 布尔列 `is_xxx`，时间列 `xxx_at`（`created_at`/`updated_at`/`deleted_at`），枚举列用 `status`/`type` 后缀。
- 外键列 `<单数实体>_id`（`user_id`）。
- 关联表名 = 两张表名单数按字母序拼接（`order` + `item` → `order_item`）。

### 4. 索引跟查询走，不跟感觉走

- WHERE 条件列、JOIN 列、排序列是索引候选；区分度低的列（性别、布尔状态）单独建索引基本无效。
- 联合索引注意最左前缀；一个表的索引不超过 5 个（写放大）。
- 唯一约束（邮箱、单号）用唯一索引，不靠应用层查重。

### 5. 迁移从第一天就开始

- schema 变更走迁移脚本（Flyway/Liquibase/alembic/prisma migrate），**禁止手改已上线库**，也禁止"删库重建"式开发进入第二周。
- 每个迁移脚本只做一件事，可回滚；涉及数据的迁移（改类型、拆列）先备份再跑。

## 常见错误（评审时见一个打回一个）

1. **大宽表**：一张表 30+ 列，什么功能都往里加列——按领域拆表，用 JOIN 换清晰。
2. **逗号分隔存 id**：`tag_ids: "1,3,7"`——多对多关联表是唯一正解。
3. **该用数值存钱用字符串/float**：金额用 decimal/int（分），浮点误差是财务事故。
4. **无索引全表扫描**：上线后慢查询 90% 是这个问题。
5. **枚举存自由文本**：`status` 列出现 "done"/"DONE"/"完成了" 三种写法——应用层定义枚举，数据库层加约束（CHECK 或外键表）。
6. **软删除只删不算**：有 `deleted_at` 但查询忘了带 `WHERE deleted_at IS NULL`——要么封装进 ORM 全局作用域，要么别用软删除。
7. **时区想当然**：时间统一存 UTC，展示层转本地；数据库时区和应用时区不一致是经典事故源。

## 什么时候不用管本文件

- 项目确定用 SQLite 且只有两三张表的 demo——按 specialist 的约定写即可
- 无持久化需求（纯静态、纯内存、外部 API 全托管数据）
- 接盘已有数据库（先读存量 schema，改继承不改风格，除非明确重构）
