# 对抗性审查：怎么找 AI 做的东西的毛病

AI 说"完成了"不算数。要从三个视角故意挑刺。

## 三视角审查

每做完一个切片，从下面三个视角各检查一遍。

### 视角 1：新用户

假装你第一次打开这个 app，什么都不懂。每次真实打开页面，只问四件事：

1. **第一次看懂**：我在哪？这里最重要的信息是什么？
2. **第一次会用**：我现在该点什么？点完会发生什么？
3. **连续用不累**：上一动作的输出有没有成为下一动作的输入？（还是每换一个页面就要重新搜索、重新选择、重新描述？）
4. **出错知道怎么办**：失败后有没有人话和 Recovery Action？

第 3 条是分水岭：如果用户需要重复输入、重复选择、复制上一步的结论，说明不是"少一个按钮"，而是**上下文连续性没有做好**——回到拆解层重新定义切片，而不是加按钮。

### 视角 2：故障制造者

故意搞破坏：

- 输入空内容会怎样？
- 输入超长内容会怎样？
- 断网时操作会怎样？
- 快速连续点击会怎样？
- 中途关掉 app 再打开，状态对吗？
- 数据为 0 或负数会怎样？

AI 写代码最容易只处理 happy path，这一步就是把它逼到墙角。

### 视角 3：审计员

假装你在审别人的代码：

- 这个改动有没有碰不该碰的文件？
- 有没有加没要求的依赖？
- 有没有硬编码密钥、密码？
- 有没有在用户输入上直接拼 SQL / 命令？
- 错误处理是不是空 catch 直接吞了？

## 两阶段 Review

### 第一阶段：自审（写完后立刻做）

AI 写完代码后，不要急着验收。新开一个对话，让它扮演审查员：

```
你现在是一个严格的代码审查员，不是作者。
下面是这次改动的 diff：

【贴 diff】

请找：
1. 边界 case 没处理的
2. 安全问题（注入、密钥、权限）
3. 错误被吞掉的地方
4. 跟项目现有模式不一致的地方
5. 可能导致崩溃的地方

不要夸，只挑毛病。
```

为什么：作者审查自己的代码有盲区。换个对话、换个角色，它才能看见问题。

### 第二阶段：亲手验证

自审通过后，自己亲手操作一遍：

- 跑测试
- 启动 app
- 走完 MVP 主链路
- 故意搞破坏（视角 2）

亲眼看到工作正常，才算真的通过。

## Code Review 看什么（按优先级）

审查按优先级走，前面的不过关，后面的先放：

1. **正确性**——逻辑对不对，边界处理了吗
2. **业务逻辑**——符合需求和项目约定吗
3. **安全性**——注入、密钥、权限、越权
4. **数据一致性**——并发下数据会串吗，事务边界对吗
5. **错误处理**——失败有人话提示吗，还是空 catch 吞了
6. **可维护性**——命名和结构，下一个读的人（和下一个 AI）看得懂吗
7. **性能**——有没有明显低效（N+1 查询、全表扫描、无上限循环）
8. **测试**——失败测试真的变绿了吗，新逻辑有覆盖吗
9. **可观测性**——关键路径有日志吗，出错了能定位吗
10. **代码风格**——和项目现有模式一致吗

最后一项是"对齐"，不是"审美"：不要把 Code Review 降级成"变量名好不好看"。前五项不过关直接打回，后五项记入待办不阻断。

## 什么时候必须升级评审

自审 + 亲手验证不够，必须正式拉一轮评审（个人项目就把"更多角色"换成"更多视角"）的情况：

- 范围变化（加 / 删功能模块）
- 核心架构变化
- 高风险数据库变更（schema 变更、数据迁移）
- 权限 / 安全变化
- 外部系统集成
- 大规模数据迁移
- 核心发布
- 生产环境变更
- 严重事故

评审的本质：**在错误成本还不高的时候，让更多相关角色发现问题。**

## Demo 成功不等于生产成功

Demo 能跑只是入场券。从 Demo 到生产之间隔着六道关，每关单独验证过，才叫"生产就绪"：

```
Demo → 真实数据 → 真实权限 → 真实并发 → 真实异常 → 真实成本 → 真实用户
```

少验证一关，上线后那关就会用事故的方式补上。

## 复盘问题清单

出了事故或审查发现大问题后，按清单复盘——目标不是"谁写错了"，是"下次怎么不再发生"：

1. 发生了什么？影响多大？
2. 时间线是什么？（什么时候引入、什么时候发现、什么时候恢复）
3. 为什么没提前发现？
4. 为什么现有门禁没拦住？
5. 为什么监控没发现？
6. 为什么恢复这么慢？
7. 哪些设计缺少冗余？
8. 哪些流程应该自动化？
9. 下一步改什么？谁负责？什么时候完成？
10. 如何验证改进有效？

## 审查不通过怎么办

- 发现小毛病（文案错、样式歪）：当场让 AI 修，算同一个切片的一部分。
- 发现大问题（逻辑错、架构歪了）：不 commit，回到上一个验证通过的 commit，重新规划这个切片。
- 发现 AI 改了范围外的代码：让它 revert，重写这次切片。

## 不要做的事

- 不要因为"差不多了"就放过明显的毛病——现在放过，上线后花十倍代价修。
- 不要让 AI 自审完就直接信——它还是会给自己找理由。
- 不要跳过亲手验证——AI 说"测试通过"和你亲眼看到"确实工作了"是两回事。
