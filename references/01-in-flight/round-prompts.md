# 每轮开口 Prompt：直接复制改括号里的内容

不同阶段给 AI 的开口句式不一样。下面这些是通用模板，把【】里的内容换成你这一轮的实际情况。

## 阶段 0：侦察（已有项目要改造时）

```
请只读检查当前项目，不要修改任何代码。
我要知道【用户任务，比如"用户怎么添加一条 todo"】现在是怎么完成的。
最后只告诉我：
1. 现在的流程是怎样的
2. 哪一步最不顺
3. 你建议的最小下一步是什么

不要改代码，不要提大重构。
```

## 阶段 1：第一条端到端链路

```
只解决一个用户可见问题：
用户输入【X】后，系统调用一个【动作】，
回答中必须出现来自【数据源】的【事实】。

先定位：
1. 输入从哪来
2. 调用什么
3. 返回什么事实
4. 失败时怎么处理
5. 怎么验证这条路通了

先提方案，我同意后再改代码。
```

## 阶段 1.5：第一条材料链路（Agent 项目专用）

```
只解决一个用户可见问题：
用户输入【X】后，系统调用一个【Tool / 检索 / 数据源】，
回答中必须出现来自该来源的【事实】。

先定位，不要直接写代码：
1. 输入从哪来
2. 调用什么能力（Tool / MCP / CLI / RAG），先用固定 Mock 结果
3. 返回什么事实，失败时返回什么（unavailable / partial / stale + Recovery Action）
4. 怎么验证这条路通了（测试命令 / 亲手看到的输出）

先提方案，我同意后再改代码。
```

为什么：Agent 项目的第一条链路必须是"输入 → 能力 → 事实"，且失败语义先于实现定好。Mock 先行，跑通再换真实 Provider，失败可回 Mock。

## 阶段 2：多步流程 / 编排

```
把【任务，比如"研究一只股票"】拆成：
材料 → 动作 → 观察 → 下一步 → 停止条件 → 输出。

先写一个最小的流程定义，不要直接写实现。
告诉我：
1. 分几步
2. 每步的输入输出
3. 哪步可能失败，失败了怎么办
4. 怎么证明这个流程工作正常

我同意流程后，再开始写代码。
```

## 阶段 3：修 bug / 对抗性审查

```
不要只看错误日志。
这个 bug 是：【现象】，我在【操作步骤】时遇到的。

用对抗性思路找最早卡住的位置：
1. 用户做了什么操作
2. 系统在哪一步开始出错的
3. 为什么之前没暴露这个问题
4. 用同一个失败案例重跑，确认修好了

修完后，把这个失败案例加入回归测试。
```

## 阶段 4：加新功能模块

```
这轮不增加无关功能。
加一个【模块名】，它的职责是【一句话】。

要求：
1. 先读现有代码，照现有模式写
2. 跨层接口先定义类型再实现
3. 只改这个模块需要动的文件
4. 写完贴出测试结果和验证截图
```

## 阶段 5：准备发布

```
这轮不增加业务功能。
目标是让项目可以打包发布。

检查：
1. 六种产品状态都有 UI 表现（Loading/Empty/Partial/Stale/Error/Retry）
2. 打包命令能跑通
3. 打包后的产物启动正常
4. 断网/出错时不白屏
5. 跑一遍完整 MVP 主链路

报告：还有哪些状态没处理，打包在哪一步可能挂。
```

## 通用提醒（每轮都可以加）

- "不要改不在这次任务范围内的代码"
- "不要加新依赖"
- "做完跑一下【测试命令】，把输出贴给我"
- "用【运行命令】启动，截图给我看"
