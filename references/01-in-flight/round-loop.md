# 中期推进：一轮 vibecoding 的 8 步循环

每做一个切片，都走这 8 步。不要跳步。

## 8 步流程

### 1. 观察：现在真实发生了什么

打开 app，亲手操作一遍。记录：
- 哪一步卡住了？
- 哪一步结果不对？
- 哪一步用户不知道下一步该干嘛？

不要凭印象，亲手点一遍。

### 2. 定义：这一轮只解决哪一个问题

一句话："这一轮做完，用户做 X 时，系统会 Y。"

不要说"优化一下体验""重构一下代码"这种模糊目标。

### 3. 拆解：这个问题属于哪一层

按四层归因：
- **缺材料**：数据没拿到 / API 没接上 / 输入不全
- **缺编排**：流程不对 / 顺序错了 / 步骤重复
- **缺标准**：不知道怎么算对 / 没有测试 / 验收不清
- **缺承载**：UI 状态没处理 / 报错看不懂 / 不能打包

### 4. 归因：为什么之前没解决

不要直接开干。先想：
- 这个问题是上一轮留下的？还是新冒出来的？
- 之前为什么没发现？
- 是我需求没说清，还是 AI 理解错了？

### 5. 提示：给 AI 一个有边界的 prompt

用 `CODING_PROMPT.md.tmpl` 的三段式（Context + Intent + Constraints）写这一轮的 prompt。关键：
- 先让 AI 读现状（"先看一下 src/api/ 里现有代码"）
- 再让它提最小切片（"先提出你打算改哪些文件，不要直接写代码"）
- 等它说清楚了，再让它动手

### 6. 执行：只改这一条用户可见路径

AI 写代码时盯着：
- 它改的文件是不是在 Constraints 范围内？
- 它有没有顺手改旁边的代码？
- 它有没有加没要求的依赖？

跑偏了立刻喊停，不要让它继续。

### 7. 审查：用另一种视角找问题

走 `adversarial-review.md`：
- 第一遍：自己亲手点一遍，看工作没
- 第二遍：新开一个 prompt，让 AI 以"代码审查员"身份独立看 diff
- 第三遍：故意搞破坏（断网、输错、快速点），看崩不崩

### 8. 回流：通过就扩大，失败就回去

- **通过**：commit（格式见 `git-discipline.md`），更新 `AGENTS.md`，开下一轮。
- **失败**：不 commit。回到第 1 步，重新观察问题到底在哪。不要在失败的基础上继续堆。

失败时先归因，再回流——按问题类型回到对应的环节，不要"哪里不好改哪里"：

| 失败类型 | 回流到 | 动作 |
|---|---|---|
| 缺材料（数据没拿到/输入不全/外部能力没接上） | 前期·材料设计 | 补材料、补 Tool、补 Provider；Agent 项目见 `specialists/agent-architecture/SKILL.md` 第一板斧 |
| 缺编排（流程不对/顺序错/上下文断了） | 中期·拆解 | 重新定义切片，先定契约再实现 |
| 缺标准（不知道怎么算对/验收不清） | 后期·验收 | 补验收标准、补 golden case |
| 缺承载（UI 状态没处理/不能打包） | 后期·承载 | 走 product-states 和 release-gate |
| AI 改坏了范围外的代码 | 本切片重做 | revert 后按 slice-discipline 重派 |

**回流后必须用同一个失败案例重跑**，验证问题真的解决——不是"再生成一次碰运气"。重跑的记录进 golden cases（`last_run` 留痕）。

## 每轮结束必须回答的四个问题

AI 做完一轮后，让它（或你自己）回答：

1. 这次改变了用户的什么行为？
2. 证据是什么？（贴测试输出/截图/终端日志）
3. 还没解决什么？
4. 如果继续做，下一轮最小问题是什么？

如果 AI 只汇报"新增了哪些文件、封装了哪些函数"，说明它跑偏了——它在汇报代码量，不是在汇报用户价值。

## 常见节奏

- 简单切片：30 分钟到 1 小时一轮
- 复杂切片：2-3 小时一轮，中间要拆更小
- 一天做 3-5 个切片比一天做一个大切片健康得多
