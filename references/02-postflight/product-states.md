# 六种产品状态：UI 在任何时刻都要会说话

用户打开 app，不是只有"正常"和"崩了"两种状态。AI 写代码最容易只处理正常路径，其他状态全是白屏或转圈。

发布前，这六种状态都要有 UI 落点。**Agent 项目（接 LLM、有工具调用的项目）额外追加三种状态**，见文末。

## 1. Loading（加载中）

**什么时候出现**：从服务器/数据库拉数据，需要等

**UI 应该表现**：
- 明确告诉用户"正在加载"，不要白屏
- 骨架屏或转圈，不要留一块空白
- 超过 3 秒要提示"有点慢"

**反例**：点了按钮，什么都没发生，用户以为卡了。

## 2. Empty（空）

**什么时候出现**：用户还没有任何数据

**UI 应该表现**：
- 明确告诉用户"这里还没有内容"
- 给一个下一步动作（"点这里添加第一条"）
- 不要用一行小字"暂无数据"敷衍

**反例**：打开列表，一片空白，用户以为出错了。

## 3. Partial（部分成功）

**什么时候出现**：主结果出来了，但有一部分数据没拿到

**UI 应该表现**：
- 显示已拿到的结果
- 明确告诉用户"有一部分没加载出来"
- 告诉用户哪部分缺了、怎么补

**反例**：一个字段没拿到，整个页面转圈不出来。

## 4. Stale（过期）

**什么时候出现**：数据是缓存的，可能不是最新的

**UI 应该表现**：
- 正常显示数据
- 角落标一下"数据更新于 5 分钟前"
- 给一个"刷新"按钮

**反例**：数据过期了但用户以为是最新的，做了错误决定。

## 5. Error（出错）

**什么时候出现**：请求失败、数据源挂了、代码 bug

**UI 应该表现**：
- 人话错误信息，不是堆栈 trace
- 告诉用户下一步能干嘛（"重试"、"稍后再试"、"联系管理员"）
- 不要白屏、不要无限转圈

**反例**：弹一个 "500 Internal Server Error"，用户不知道该干嘛。

## 6. Retry（重试）

**什么时候出现**：出错后用户可以重试

**UI 应该表现**：
- 一个明显的"重试"按钮
- 重试时按钮变 loading 状态
- 重试成功自动恢复，失败再显示错误

**反例**：出错后用户只能刷新页面重来。

## 检查方法

发布前，故意制造这六种状态：

| 状态 | 怎么制造 |
|---|---|
| Loading | 在 API 调用里加个 `sleep(2000)` |
| Empty | 清空数据库 |
| Partial | 让某一个字段的请求失败 |
| Stale | 缓存 TTL 设短一点 |
| Error | 断网 / 关数据库 |
| Retry | 出错后点重试 |

每种状态下截图，确认 UI 都"会说话"。

## 不做的事

- 不要用一个万能 toast 把所有错误都盖过去
- 不要在 UI 里显示技术错误（堆栈、HTTP 状态码、SQL 错误）
- 不要假设用户懂技术——"连接超时"比"ETIMEDOUT"好，"网络好像不太好，请检查一下"比"连接超时"更好

## Agent 项目追加三态（接 LLM / 有工具调用的项目）

普通的六态覆盖不了 Agent 特有的失败面。项目用到 LLM、Tool、Provider 时，下面三态也要有 UI 落点，并各造一次留证：

### 7. Provider unavailable（外部能力不可用）

**什么时候出现**：模型 API 挂了、限流 429、超时、数据 Provider 不可用。

**UI 应该表现**：
- 人话说明哪个能力不可用（"行情数据源暂时连不上"），不是 "fetch failed"
- 给 Recovery Action：重试 / 切换数据源 / 稍后再试 / 用缓存数据（标 stale）
- 如果有降级路径（强模型→弱模型、真实 Provider→Mock），告诉用户"正在用备用方式，结果可能不全"

**反例**：整个页面转圈到超时，或者裸着一个 502。

### 8. Runtime unavailable（运行时不可用）

**什么时候出现**：Agent Runtime 启动失败、崩溃、会话无法恢复。

**UI 应该表现**：
- 明确说"助手核心没起来"，并给诊断入口（错误 ID / 查看日志 / 重启）
- 已保存的历史数据不受影响，用户能看到之前的成果
- 不假装正常——没有 Runtime 时按钮要么禁用并说明原因，要么走单轮降级模式

**反例**：界面看着正常，点任何按钮都没反应或静默失败。

### 9. Completed with warnings（带警告完成）

**什么时候出现**：任务跑完了，但有关注点：部分数据缺失、结论证据不足、用了降级模型、超出预算被裁剪。

**UI 应该表现**：
- 正常展示结果，但**明确列出警告**（哪部分数据缺失、哪个结论证据弱）
- 警告是可操作的：点一下能看到缺什么、怎么补
- 不要悄悄把 Partial Success 报成完全成功——这是评测维度里"证据"和"结果"两维都要抓的

**反例**：报告看起来完整，实际两个字段是空的有证据是编的，用户当完全可信用。

| 状态 | 怎么制造 |
|---|---|
| Provider unavailable | 断开模型/数据 API，或把 endpoint 改错 |
| Runtime unavailable | 让 Runtime 启动脚本失败 / 中途 kill 进程 |
| Completed with warnings | 让某一个数据源返回 partial 或 stale |
