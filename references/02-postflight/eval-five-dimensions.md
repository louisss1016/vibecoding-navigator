# 五维评测：凭什么相信做完了

功能写完后，从五个维度检查。任何一维不过关，都不算完成。每维必须给出**可执行的检查动作**和**留痕的证据**——打勾游戏不算评测。

## 1. 结果（Outcome）

**问题**：用户要的事真的完成了吗？

检查：
- 亲手走一遍 MVP 主链路，从头到尾结果对不对？
- 输出是不是用户要的，不是 AI 以为用户要的？
- 跟 PROJECT.md 里的验收标准逐条对，每条都打勾了吗？

## 2. 过程（Trajectory）

**问题**：它是怎么做到的？过程合理吗？

检查：
- 有没有调错 API / 走错流程？
- 有没有无意义的重试？
- 步骤数合理吗？（加一条 todo 调了 10 个 API 就是不合理）
- 中间有没有出错被吞掉？

## 3. 证据（Evidence）

**问题**：结论能回到材料吗？

检查：
- UI 上显示的数据，真的来自数据库吗？还是 AI 编的？
- 关键数字能对上吗？（输入 3 笔，总额是 3 笔的和吗？）
- 刷新页面后数据还在吗？

**证据格式与落盘位置见 `docs/evidence-format.md`**——测试输出贴全文、截图落盘、AGENTS.md 引用路径，三段缺一不可。

## 4. 安全（Safety）

**问题**：有没有越权、泄露、危险操作？

检查：
- 有没有硬编码密钥、API key？（自动扫描：`scripts/gate.sh` 第 3 项）
- 用户输入有没有直接拼 SQL / 命令？
- 错误信息会不会泄露系统路径、堆栈、内部结构？
- 危险操作（删除、外发）有没有确认？
- 两个用户的数据会不会串？
- 依赖有没有已知漏洞？（自动扫描：`scripts/gate.sh` 第 4 项，npm audit / pip-audit）

## 5. 成本（Cost）

**问题**：跑得动吗？烧得起吗？

### 性能成本（有测量命令，不许凭感觉）

| 指标 | 测量方法 | 参考阈值 |
|---|---|---|
| 启动时间 | `time npm run dev`（或 hyperfine）；Web 用 Lighthouse | > 5 秒要注意 |
| 操作响应 | 浏览器 DevTools Network 面板；或 `curl -w "%{time_total}" -o /dev/null -s <url>` | > 1 秒要优化 |
| 内存占用 | `ps aux \| grep <进程>` / 任务管理器；记录初始值 | 长时间用对比看涨不涨 |
| 内存泄漏 | 重复核心操作 50 次，每 10 次记一次内存 | 曲线应平稳，持续上涨 = 泄漏 |
| 包体积（Web） | `npm run build` 后看产物大小；`npx vite-bundle-visualizer` | 首屏 JS > 500KB 要管 |

### Token / API 成本（vibecoding 项目特有的死法）

- 统计每轮 vibecoding 的 token 用量（API 账单或 agent 的用量面板），异常飙高的轮次 review prompt 哪里失控。
- 产品自身调 LLM 的：估算单用户月成本 = 每次操作 token 数 × 操作频率 × 单价，写进 PROJECT.md 的约束。
- 警惕无限重试烧钱：重试必须有次数上限和退避，这是 golden case（double-submit）要覆盖的。
- 免费额度（Vercel/Supabase/数据库）快用完时，成本维直接 ❌——上线即欠费。

## Agent 项目的七项细查（接 LLM / 有工具调用时加查）

普通项目五维够了。Agent 项目的质量不只体现在最后一句话，也体现在它做了什么、怎么做、有没有绕过边界——按这张表细查：

| 归属 | 细查项 | 关注点 | 失败信号 |
|---|---|---|---|
| Outcome | 用户要求满足度 | 是否回答真实问题，是否遗漏约束 | 答非所问、跳过限制 |
| Outcome | 交付格式 | 是否符合报告/方案/行动项结构 | 结构缺失、风险未标注 |
| Evidence | 事实可靠性 | 结论是否有依据，是否把推测写成事实 | 无来源、强断言、幻觉 |
| Evidence | 证据充分性 | 关键判断能否回到材料、工具结果或 Trace | 结论和证据断裂 |
| Trajectory | 逻辑闭合 | 从材料到结论有无跳步和矛盾 | 因果倒置、前后冲突 |
| Trajectory | 工具使用合理性 | 是否调用正确工具、参数是否合理 | 没查就答、乱调工具 |
| Safety | 安全与权限 | 越权、泄露、危险动作、注入 | 未确认写操作、暴露敏感信息 |

**Partial Success 不许被误报**：部分完成既不是完全成功也不是完全失败，按 partial 记，警告进 Completed with warnings 状态（见 product-states）。

## 评测工程化（从"测过几轮"到"可回归体系"）

| 环节 | 要求 |
|---|---|
| 三类评分器 | 确定性检查（能自动跑的）/ LLM-as-a-judge（主观质量）/ 人工复核（视觉、手感）——golden-cases.json 的 `verify.type` 就是按这个分的 |
| 基线管理 | 每次改动和上一个通过版本比，说清"变好还是变坏、和谁比"，不跟感觉比 |
| 稳定性 pass^k | 关键用例连跑 k 次（建议 3）都过才算过——碰运气过的用例是定时炸弹 |
| Trace 可还原 | 过程证据能复现"Agent 做过什么"，不只是存最终答案 |
| CI 回归 | 自动部分进 `scripts/gate.sh`，每次改动后自动跑，不想起来才跑 |

## 不通过时回流到哪（AuditDecision）

评测/审计不通过时，按归因回流，不要"再生成一次碰运气"：

| 失败类型 | 回流目标 | 动作 |
|---|---|---|
| 缺材料 / 数据过期 / 来源不明 | 材料与能力设计（Agent 项目见 agent-architecture 第一板斧） | 补充读取/检索/工具调用，降级结论或补 provenance |
| 推理不闭合 / 证据和结论断裂 | 编排（round-loop 重新拆解） | 重组推理链、调整 Prompt/Skill |
| 权限或隐私风险 | 安全门禁 | 阻断、降级、请求人工确认 |
| 格式不完整 | 输出契约 | 重新执行输出契约检查 |
| 超出成本预算 | 编排 + 成本治理 | 压缩、减少重复调用、降级或终止 |

回流修正后，**必须用同一失败用例重跑**验证，记录进 golden cases 的 `last_run`。

## 怎么打分

每维分三档：

- ✅ 通过：按上面的方法**测量/亲眼验证过**，证据留痕
- ⚠️ 有问题：不影响主流程但要记下来（写进 release note）
- ❌ 不通过：必须修，不修不能发

任何一维 ❌ 都不能进发布门禁。

## 项目级质量指标（不要只看 Bug 数量）

单次功能验收之外，项目层面按四类指标观察质量走向。指标是仪表盘不是 KPI 考核——用来看趋势、找短板，不是拿来包装：

| 类别 | 指标 | 说明 |
|---|---|---|
| **交付效率** | Lead Time（一个需求从提出到上线多久）/ Deployment Frequency（多常发一次）/ Release Cycle Time（发布周期） | 观察吞吐，越短越勤通常越健康 |
| **交付稳定性** | Change Failure Rate（变更失败率）/ Failed Deployment Recovery Time（失败部署恢复时间）/ Deployment Rework Rate（部署返工率） | DORA 体系核心四项（含部署频率），观察"快而不翻车" |
| **产品质量** | 线上缺陷数 / 客户投诉 / 核心流程成功率 / 性能 / 可用性 | 用户真正感知到的质量 |
| **业务结果** | 使用率 / 转化 / 成本 / 收入 / 节省时间 / 人工替代率 / 客户满意度 | 最终裁判：业务价值优先，前三类都是为它服务的 |

个人项目至少每月看一眼前两类（git log 就能数出来），别让"感觉最近挺快"代替真实数字。

## 输出

把五维检查结果贴在 AGENTS.md 或 release note 里，证据按 `docs/evidence-format.md` 落盘：

```markdown
## 验收记录

| 维度 | 结果 | 备注 |
|---|---|---|
| 结果 | ✅ | 主链路走通，5 条验收标准全过 |
| 过程 | ✅ | 加 todo 只调了 1 个 API |
| 证据 | ✅ | 刷新后数据还在；输出见 docs/evidence/slice-3/ |
| 安全 | ⚠️ | 错误信息暴露了文件路径，下版修 |
| 成本 | ✅ | 启动 1.2s，操作响应 <200ms；50 次操作内存平稳 |
```
