# Golden Cases：回归用例清单

每次改代码，最怕"修了 A 坏了 B"。Golden cases 就是一组固定的用例，每次改完都跑一遍，确保没把之前修好的东西弄坏。

## 怎么建立

不需要一上来写 12 条。每个切片做完，遇到一个 bug 就加一条。慢慢地就攒起来了。

## 机器可读格式（必须）

用例存放在项目的 `tests/golden-cases.json`，模板在 `references/02-postflight/golden-cases.json.tmpl`。每条用例：

```json
{
  "id": "offline",
  "title": "数据源不可用",
  "category": "error",
  "steps": "断网后执行核心操作",
  "expected": "显示人话错误，不白屏",
  "verify": { "type": "command", "cmd": "npm test -- offline" },
  "related_slice": "commit hash 或切片名",
  "last_run": { "date": "", "result": "" }
}
```

- `verify.type`：`command` = 自动跑（`scripts/gate.sh` 会执行）；`manual` = 必须人眼（UI 视觉、交互手感）。
- `category`：normal / error / state / data / **agent**（Agent 项目专用）——发布前按分类跑，变更后按影响范围跑（映射表见 `change-management.md`）。
- `last_run` 每次跑完更新，这是"最近一次真实验证"的证据，AGENTS.md 引用它而不是聊天记录。

## 一个功能至少验证四件事

设计用例时按这四类想，比凭感觉列要全：

1. **正常路径**——标准输入，主链路走通
2. **边界条件**——空输入、1 条、100 条、超长字符串、0 和负数
3. **异常路径**——数据源挂了、某一步部分失败、非法输入
4. **权限 / 安全**——没权限的用户看不到不该看的，越权操作被拦

前三类决定"功能能不能用"，第四类决定"敢不敢上线"。下面的必备用例就是按这四类展开的。

## 必备用例（至少要有这些）

Agent 项目（接 LLM / 有工具调用）除下面的通用用例外，还必须有 `agent` 类用例：会话隔离、Provider 部分数据、Trace 可还原、超预算降级、pass^3 稳定性——模板里已内置，见 `golden-cases.json.tmpl`。

### 正常路径

1. **主链路能跑通**：从打开 app 到完成核心动作，一气呵成
2. **空输入**：什么都不输直接提交，应该有合理提示，不能崩
3. **边界值**：输入 1 条、输入 100 条、输入超长字符串

### 错误路径

4. **数据源不可用**：断网 / 数据库没起 / API 挂了，app 应该显示人话错误，不能白屏
5. **部分失败**：某一步失败了，但已有结果还能用（比如"加载列表失败了，但上次的数据还在"）
6. **非法输入**：输入 SQL 注入字符串、HTML 标签、负数，不能崩

### 状态

7. **重启恢复**：操作到一半关掉 app，再打开应该恢复到之前的状态
8. **取消操作**：点了"取消"后，不能继续跑，不能留下半成品
9. **重复点击**：快速点十次同一个按钮，不能崩、不能重复提交

### 数据

10. **刷新后数据还在**：操作完刷新页面，数据不丢
11. **数据为零**：刚打开 app 还没有任何数据，界面不能崩
12. **长数据**：几百条记录，滚动不卡

## Case 挂了：缺陷怎么记

Case 跑出问题，记一条缺陷再修。最小字段集（记不全也要有前六项）：

```markdown
标题：【一句话说清什么坏了】
环境：【开发机 / 测试服 / 哪个浏览器哪个系统】
版本：【commit hash 或版本号】
复现步骤：【1. 2. 3. 别人能照着走一遍】
期望结果：【应该怎样】
实际结果：【实际怎样】
影响范围：【谁受影响、影响多大】
严重程度：【见下】
优先级：【见下】
日志/截图：【evidence 路径】
```

**Severity ≠ Priority**：Severity 是问题本身有多严重（崩了 vs 文案歪了），Priority 是应该多快处理（今晚修 vs 下个版本修）。低频但高风险的漏洞，Severity 高但如果有临时隔离措施，Priority 可以降——先缓解、再排期。两者分开记，团队（和你自己）才不会为"到底多严重"吵架。

修完之后：补一条复现 golden case（先红后绿），更新缺陷的"验证结果"和"关闭原因"。

## 什么时候跑

- 每个切片 commit 前，跑一遍相关的 case
- 发布前，全部跑一遍——自动部分进 `scripts/gate.sh`，手动部分过人眼级 release-gate
- 改了核心模块（数据库、API、路由），全部跑一遍
- 需求变更后，按 `change-management.md` 的影响映射表确定重跑范围

## 自动化 vs 手动

- 简单的主链路、输入输出：写自动化测试（pytest / jest / playwright）
- UI 视觉、交互手感：手动跑，`verify.type` 标 `manual`
- 不要追求 100% 自动化——手动跑主链路 5 分钟的事，比写自动化脚本 1 小时更值

## 不做的事

- 不要一开始就写 100 条 case——写不过来，也维护不动
- 不要把"看起来合理"当通过——每个 case 都要亲手跑过，`last_run` 要留痕
- 不要跳过错误路径的 case——happy path 谁都会写，错误路径才是产品质量的分水岭
