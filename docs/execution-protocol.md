# 执行层协议：什么时候起子 agent、怎么派工、怎么收活

 specialist 只是知识（"怎么写"），子 agent 才是干活的手。这个文件定义编排层（主 agent）怎么把活派给子 agent、怎么验收子 agent 的活。

## 三层架构

```
┌─────────────────────────────────────────────┐
│ 编排层（主 agent / 主 skill）—— 流程所有权      │
│ 做什么、做到哪算完、下一轮做什么、验收、发布    │
│ 需求澄清、MVP 裁剪、选型、变更评估——永不外包    │
└──────────────┬──────────────────────────────┘
               │ 派工单（Dispatch Ticket）
               ▼
┌─────────────────────────────────────────────┐
│ 执行层（子 agent × N）—— 按 specialist 路由    │
│ 每个子 agent = 一个领域切片 + 对应专家知识      │
│ 上下文隔离、可并行、可替换、可当黑盒评测         │
└──────────────┬──────────────────────────────┘
               │ 五要素回报（缺一即未完成）
               ▼
┌─────────────────────────────────────────────┐
│ 知识层（specialists/）—— 子 agent 的系统提示词  │
│ 每个 specialist 头部带机器可读契约块            │
└─────────────────────────────────────────────┘
```

比喻：编排层是包工头，知识层是工种手册，执行层是进场工人。手册再好，没有派工单机制，包工头自己捧着六本手册挨个干——干一件污染一次脑子，还没法同时开工。

## 什么起子 agent，什么不起

| 起子 agent（执行层干） | 编排层自己干（永不起子 agent） |
|---|---|
| 领域实现切片（按 specialist 路由） | 需求澄清、反问用户（questioning-rules） |
| 独立代码审查（对抗性审查天然适合——"作者审自己有盲区"，换上下文就是换脑子） | MVP 裁剪、第一版做什么不做什么 |
| 打包 / 构建验证 | 技术选型 |
| golden cases 批量执行 | 验收判断、发布门禁决策 |
| 跨层切片的各方实现（契约定死后可并行） | 变更评估、回退决策 |
| 文档生成（README、release note） | 任何需要跟用户反复确认的事 |

原则：**子 agent 只回答"怎么写"，编排层永远握着"做什么、做到哪算完"。**

## 派工单（Dispatch Ticket）格式

每次起子 agent 之前，编排层必须把下面六项写全，缺一项不派工：

```markdown
## 派工单 — <切片 ID>

1. 切片定义：用户做【X】时，系统会【Y】。（一句话，来自 round-loop 第 2 步）
2. 接口契约：【跨层类型定义，输入/输出/错误信封。编排层定死，子 agent 无权改】
3. 禁区：【不许碰的文件/目录，来自 AGENTS.md 的"禁区"section】
4. 专家知识：【挂哪个 specialist，子 agent 先读它的 SKILL.md 再动手】
5. 验证命令：【跑什么命令，期望看到什么。没有验证命令 = 没有验收标准】
6. 硬规则：不要改范围外代码；不要加新依赖；先提方案我确认后再写代码。
```

第 6 条对应 slice-discipline：**先读现状、先提最小切片方案、被批准后才动手**。子 agent 的第一轮回报应该是"我打算改哪几个文件、每步做什么、怎么验证"，不是代码。

## 子 agent 回报五要素

子 agent 说"完成了"的时候，必须带回五样东西，缺任何一样都视为未完成（这是铁律 4 的执行层版本）：

```markdown
1. 文件清单：改了/新增了哪些文件（路径列表）
2. 验证命令 + 原始输出全文：跑了什么命令，输出贴全文，不许摘要成"测试通过"
3. 证据路径：截图/日志落盘到 docs/evidence/<切片 ID>/，列文件路径
4. 自审结论：以审查员视角过一遍自己的 diff，列出发现的边界 case / 安全问题 / 被吞掉的错误
5. 冲突标记：与其他子 agent 的契约、或与禁区不一致的地方——只标记，不自行决策
```

编排层收到五要素后才进入 round-loop 第 7 步（对抗性审查）。发现子 agent 只汇报"新增了哪些函数、封装了哪些类"而没有用户可见行为和证据，直接打回——它在汇报代码量，不是汇报价值。

## 并行规则

只有同时满足以下两条，才允许并行起多个子 agent：

1. **契约已定死**：跨层接口类型在派工单里写清楚，各方按契约实现，不许私下改类型。
2. **文件范围无交集**：两个派工单的"禁区"互为对方的"只改范围"。

并行时的纪律：

- 并行子 agent 之间**不许互相读代码**，只认契约。后写的一方要对齐，等编排层合并后跑对接测试。
- 并行完成后，编排层必须做一次**对接验证**（两个领域合起来跑主链路），再分别 commit。
- 任何一个子 agent 回报缺要素，整个并行组不 commit，回到缺要素的那个切片重做。
- 子 agent 之间**只传结构化中间结果**（结论、证据、风险、不确定性），不传递无边界的完整聊天记录——上下文膨胀是多 Agent 失效的第一原因。

## 多 Agent 升级判据（起子 agent 前先问一遍）

起子 agent 本身已经是"多 Agent"的雏形，所以升级要有真实失效信号，不许为复杂而复杂。**默认顺序不许跳级**：

```
编排层自己干 → 起一个领域子 agent → 起多个并行子 agent → 起 Generator + Critic 双角色
```

| 失效信号 | 该不该加子 agent |
|---|---|
| 单上下文同时背着多个领域的规范，注意力稀释、开始跑偏 | 该按领域拆（当前默认做法） |
| 一个上下文既要写代码又要审查，自审流于形式 | **该起独立 Critic 子 agent**（author 审自己有盲区） |
| 有天然可并行的独立切片，且契约定死、文件范围无交集 | **该并行起多个** |
| 不同子任务需要不同工具权限/系统访问 | 该按权限隔离，一个子 agent 一个权限面 |
| 上下文越来越长，模型遗忘前文 | 先压缩/外置（见 agent-architecture 的 Token 治理），不行再拆 |
| 简单任务、单轮问答、边界不清 | **不该起**——编排层自己干更快 |
| 只是为了"看起来架构复杂" | **不该起** |

多子 agent 的价值不是产量翻倍，而是**角色、上下文、权限和责任边界的拆分**。拆完没有清晰边界和交付契约，只是把混乱复制 N 份。详细的失效信号根因和角色分工（Router/Worker/Synthesizer/Critic）见 `specialists/agent-architecture/SKILL.md` 第二板斧。

## 仲裁规则（ownership-matrix 的运行时版）

子 agent 之间意见冲突时，按这个顺序裁，不许自己偷偷选一个：

1. **契约问题**（类型、接口、数据格式）→ 编排层。契约是编排层定死的，子 agent 无权改，只能标记。
2. **领域内怎么写**（这个栈的习惯、库的用法）→ 对应的 specialist 子 agent。
3. **跨领域冲突**（React 专家说用 context、TypeScript 专家说用 discriminated union）→ 按 `docs/ownership-matrix.md` 的所有权表裁，各管各的层。
4. **裁不动** → 把 trade-off 原样 surfaced 给用户，让用户定。不要替用户拍板，也不要假装两个专家一致。

## specialist 契约块

每个 specialist 的 SKILL.md 头部必须带机器可读契约块，编排层派工前读它决定路由和禁区：

```markdown
---
name: <specialist 名>
description: <触发描述>
contract:
  owns: [这个专家说了算的领域列表]
  input: [派工单里必须给它的东西]
  output: [它必须回报的东西]
  forbidden: [它不许碰的决策]
---
```

- `owns` 和 `forbidden` 与 `docs/ownership-matrix.md` 的所有权表保持一致，两边打架时以 ownership-matrix 为准并修 specialist。
- 新增 specialist 时必须填契约块，并在 `docs/stack-routing.md` 加路由行、在 ownership-matrix 加边界说明——三步缺一不可。

## 常见错误

- **把整个功能派给一个子 agent**：一个子 agent 只拿一个领域切片。"做个设置页"要拆成 UI / 存储 / 测试三个派工单，不是一张。
- **派工单不写验证命令**：子 agent 没有验收标准，就会用"我觉得没问题"交差。没有验证命令的派工单不派。
- **让子 agent 自己定契约**：它改了类型不告诉你，对接时崩了都不知道哪边的锅。契约只能编排层定。
- **子 agent 冲突时和稀泥**："两边都有道理，折中一下"——按所有权表裁，裁不动问用户。
- **审查也外包给写代码的同一个上下文**：审查必须新起子 agent（新对话），作者审自己的代码有盲区。
